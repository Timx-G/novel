## 一篇文章怎样使用 Spec

第一次处理某篇时，在 `specs/chapters/<篇名>/` 建立以下三个简短文件。此后同一篇持续维护这一套 Spec，每轮更新当前目标与实际结果、保留迭代记录。新章节才建立新的单篇 Spec，不为同一篇的每次修订复制一套平行文件。

| 文件 | 起草前写清什么 | 编辑后更新什么 |
| --- | --- | --- |
| `requirements.md` | 本次要写或改的内容、材料来源、作者已确认的意思、保留内容、尚不确定之处 | 新补充的事实、立意变化、作者实际采纳的决定 |
| `plan.md` | 展开顺序、详略安排、本轮修改任务；建议与决定分开 | 已完成的任务、剩余工作及调整原因 |
| `validation.md` | 与该篇相关的验收项、核对方法和预期 | 实际结果、稿件或素材位置、作者反馈、通过或待确认状态 |

## 章节、迭代与 Git 合并

| 层次 | 记录在哪里 | 完成意味着什么 |
| --- | --- | --- |
| 章节状态 | 全书目录 | 待写、初稿、修改中或暂定稿；反映当前稿件成熟度 |
| 本轮迭代 | 单篇 Plan 与 Validation | 本次约定范围已交付、相关核对已执行、剩余问题已记录 |
| Git 合并状态 | 单篇迭代记录与 Git 历史 | 本轮改动已进入 main；不代表整章或整本书已经定稿 |

main 保存当前整合版本，可以包含明确标为初稿的文章。分支对应一轮有边界的工作，例如“交付第一版”或“补入一次重逢的细节”；不让一条分支承担某一章未来全部修改。

1. 开始一轮时，写清本次材料、影响的篇目、交付目标和核对项。当前必需的材料缺失，应保留不确定性、缩小范围或澄清；不能凭空填补。
2. 完成本轮要求，处理已经发现的事实冲突与原意偏移，并在 Spec 中记录尚未提供的细节和未来反馈。未来可能继续完善，不影响本轮独立交付。
3. 按本轮目标核验并提交；获授权合并时将正文与对应 Spec 一起整合，按 `book-reading-edition` 核对钩子生成的阅读版并检查排版。导出失败时保留旧版并说明，不影响对 Git 已完成状态的准确记录。只在实际执行后记录“已合并”，不把主干认可等同为完整稿已获认可。
4. 上一轮合并后，从最新 main 新建下一轮分支。新章建立自己的 Spec；旧章修订更新原有 Spec。已合并的 Spec 保留在项目中，不因分支结束而删除。
5. 新材料若同时影响前后两章，在本轮 Plan 列出两篇及各自改动，更新它们的正文、Spec 和相关索引后一起核对；不把“以后可能有补充”当成等待未来章节完成的阻塞依赖。

后续待办与本轮任务分开。只有作者明确要求定稿或已认可当前稿件时，才将章节标为“暂定稿”；它与一次分支合并不是同一个动作。

常规循环：**核对素材与要求 → 确定本轮写法 → 起草或改稿 → 对照素材核验 → 接收反馈 → 更新稿件与 Spec**。

作者已明确要求起草或修改时，完成相应 Spec 与稿件，不为每一步重复请求确认。缺口不影响原意时可以先写有依据的部分；涉及真实事件、立场或关系结局的关键歧义，只追问必要问题。只讨论时不自动改文件。

轻度润色只更新受到影响的内容，不为标点修改重新做整套规划。只有全书目标、表达方向或推进范围发生实质变化时，才调整全局 Spec；新的个人理解可以先留在相关篇目。

## 单篇验收与状态

按每篇实际情况选择验收项，起草前记入该篇 `validation.md`，未检查的项目保持“未核验”。

- **原意与事实**：对照素材及作者补充，检查是否新增事实、替换立场、强化确定性，或把今天的理解写成当时已经明白。
- **表达与推进**：人物和指代可理解，段落带来新的事件、观察或思考；未为篇幅重复感慨或堆砌术语。
- **本篇边界**：检查该篇特有的问题，例如重逢篇不预定关系结束或重新开始已成事实，实习篇不将未证实的公司行为写成事实。
- **版本与接续**：重大修改已归档，正文链接与目录状态一致，待解决问题有记录。
- **作者反馈**：记录作者认同和不认同的具体表达。编辑核对通过不等于作者认可；尚未收到反馈时标为“待作者反馈”。

正文状态沿用目录中的“待写、初稿、修改中、暂定稿”。Spec 建好仍是“待写”；实际生成正文才进入“初稿”。“暂定稿”依据作者认可或明确的定稿授权，不由助手把检查通过等同为认可。

获授权编辑完成后，更新相关单篇 Spec、目录和必要协作记录。有了实际作品与可回看的认识，再补充回看索引。
