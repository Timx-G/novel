# Tech Stack｜表达方式与写作约定

这里沿用 SDD 的文件名，内容记录本书的表达方法、材料边界与写作载体。目标见[Mission](mission.md)，执行过程见[Roadmap](roadmap.md)。

## 已确认的表达方向

- **朴素、具体、接地气。** 普通读者不需要文学或技术背景，也能理解人物、事件和想法。
- **保留作者自己的声音。** 整理口述中的语病、重复和指代，不替换作者立场；保留自然的幽默、自嘲、情绪和有作用的停顿。
- **用真实材料组织叙事。** 人物、动作和细节必须有依据；有意义的心理活动与思考可以展开，素材少时允许简短。
- **让理解逐渐形成。** 区分“当时的我”与“现在回看的我”，保留认识的变化。
- **结尾随材料而定。** 不强制反转、升华、治愈或圆满，也不要求每篇重复“不要怕”。

## 第一轮的编辑起点

以下是依据现有素材采用的编辑方式，后续由实际稿件校准，不视为作者已经认可所有具体写法：

- 以第一人称叙述为起点；只在作者授权且材料支持时调整视角。
- 先找到一件事或一个问题，再安排背景、感受与回看；不把“经历—感受—思考—认识—提醒”固定成每篇的五段模板。
- 较长经历先概述，再展开真正影响理解的片段；不为了增加画面补造天气、物件、对白或他人心理。
- 涉及技术经历时，只解释理解故事所需的术语。写作的管理流程留在 Spec，正文按作品需要表达。
- 标点、长短句、口语和重复按上下文判断，不用机械禁词表决定文风。

## 材料与判断

- 亲历、回忆、听闻、感受和推测分别处理。不确定的信息保留限定，不把推测润色成事实。
- 他人的原话只在有依据时作为引语；只记得大意就转述。诗句、观点和公开事件保留来源，需要使用时再核实。
- 一个人的感受不能自动代表另一方的意愿；个人解释不能自动成为事件的唯一原因。
- 有矛盾或逻辑跳跃时指出具体问题，讨论可能的解释；作者的疑问、助手的解释与作者已经确认的认识分开。
- 新补充可以修正旧理解。保留原始材料，并在相关 Spec 或协作记录写清修正，避免后续继续采用已过时的判断。

## 写作载体与版本

| 内容 | 维护位置 |
| --- | --- |
| 原始素材 | [现有零散素材](../01-素材.md)、[素材目录](../01-素材/)及作者指定的其他文件，保持原位置 |
| 全书目标与表达方法 | 本目录中的 Mission、Tech Stack、Roadmap |
| 单篇写作要求、计划与验收 | 开始处理该篇时，按 Roadmap 建立对应 Spec |
| 正文 | [正文目录](../02-正文/)，一篇一个主要 Markdown 文件 |
| 篇目状态与阅读顺序 | [全书目录](../00-全书规划/全书目录.md) |
| 作者决定与接续事项 | [协作记录](../00-全书规划/协作记录.md) |
| 当前封面与选用依据 | [封面说明](../03-附件/封面/封面说明.md)，图片随项目保存 |

使用 UTF-8 Markdown，沿用现有 Obsidian 工作区与相对链接。对同一篇的结构重排、大幅删减或视角变更，先完整归档再修改。具体保护规则见[协作约定](../AGENTS.md)。

## 怎样校准表达

作者指出“这句话不像我”“这里过度解释了”或“这段想保留”时，优先修正对应稿件与单篇 Spec。作者明确认可为全书偏好后，再更新本文件。书籍特定决定留在本项目，通用写作 skill 不因一次反馈自动改写。
